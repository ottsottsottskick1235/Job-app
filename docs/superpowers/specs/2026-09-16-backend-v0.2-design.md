# Job App Backend v0.2 Design

## Goal
Turn the prototype into an authenticated, multi-tenant backend that can support real worker and employer accounts, multiple employer locations, geocoded addresses, explainable automatic matching, advanced filtering, safe application workflows, and auditable state changes while keeping the UI deliberately plain.

## Architecture
The application remains Next.js App Router + TypeScript + Supabase/Postgres. Supabase Auth owns identity. Public clients use only the anon key for authentication; all domain mutations flow through authenticated Next.js API routes. Server routes use the Supabase service-role client after verifying the caller's access token and enforcing authorization in application code. Postgres RLS is enabled as defense in depth.

Domain services are separated from transport code: auth/authorization, matching/scoring, search filters, application state transitions, geocoding, and audit events each have focused modules. The existing hard-rule matcher remains the source of eligibility. A soft 0-100 score only ranks already-eligible pairs and never overrides hard requirements.

## Identity and tenancy
- `profiles` links one Supabase Auth user to an account type: `worker` or `employer`.
- Workers keep a separate `workers` domain record linked to `auth.users` through `user_id`.
- Employer companies remain `employers`; `employer_memberships` links authenticated users to companies with `owner`, `admin`, `recruiter`, or `viewer` roles.
- A user may belong to multiple employer companies.
- Authorization helpers resolve the authenticated user from `Authorization: Bearer <access_token>` and check ownership/membership before any read or mutation.

## Locations and geocoding
- `worker_locations` stores one or more worker locations, with one primary matching origin.
- `employer_locations` stores named business locations and normalized address fields.
- Jobs reference an employer location and also store latitude/longitude snapshots for deterministic matching.
- `/api/locations/geocode` uses server-side Nominatim/OpenStreetMap-compatible geocoding. Queries are normalized and cached in `geocode_cache`; provider URL and user agent are configurable through environment variables.
- Location records retain provider metadata and geocoded timestamps.

## Jobs and worker preferences
Jobs gain employment type, workplace type, pay range, currency, optional end/closing dates, openings, and filter metadata. Workers gain preferred employment/workplace types and role keywords. Existing certifications, shifts, experience, pay, weekly hours, and travel radius remain hard-match inputs.

## Matching
Hard eligibility rejects role/category mismatch, pay below worker minimum, insufficient experience, excess travel distance, weekly-hour mismatch, missing/expired certifications, uncovered shifts, incompatible employment/workplace types, inactive workers, and non-open jobs.

Eligible pairs receive an explainable score from distance, pay surplus, experience surplus, weekly-hours fit, schedule flexibility, and preference alignment. The score is stored on `applications` with a JSON breakdown and matcher version. Upsert remains idempotent on `(worker_id, job_id)`. Matching can run for one worker, one job, or all pairs, and each run is logged.

## Filtering and discovery
Server-side filtering supports text query, categories, employer, employment/workplace type, pay, weekly hours, experience ceiling, required certifications, weekdays, start/closing dates, geographic radius, application status, score range, and sorting. Saved searches store named JSON filter sets for authenticated users.

## Application state machine
Allowed transitions are explicit and actor-aware:
- `submitted` -> `employer_interested` or `rejected` by employer
- `submitted` -> `withdrawn` by worker
- `employer_interested` -> `worker_accepted`, `worker_declined`, or `withdrawn` by worker
- `worker_accepted` -> `hired` or `rejected` by employer

Every transition records an `application_events` row with actor, previous status, next status, reason, and timestamp. Invalid transitions are rejected before touching the database.

## API and security
- Zod validates mutation payloads.
- List endpoints are paginated.
- Stable JSON errors include `code` and `message`.
- Sensitive reads are scoped to the authenticated worker or employer membership.
- Service-role key stays server-only.
- Caller identity is never trusted from request body IDs when auth can derive it.
- RLS is enabled on user data tables.
- SQL constraints protect relationships and numeric ranges.
- Geocoding is server-side and cached.

## Testing
Pure domain logic is covered first: matching/scoring, application transitions, filters, and geocoding normalization. Route code stays thin so domain behavior remains independently testable.

## Non-goals
No visual redesign, payments, chat, payroll, identity verification, resume parsing, or production observability platform in v0.2.
